## 1. 需求 1：財務部同仁改由人資主管核

- 新常數 `STORE_ATT_HR_ONLY_DEPTS = ['fin']`（要加部門只改這裡）。
- `attNeedOf_`：總部 hs、主要部門在清單內 → `{kind:'hr_only', dept}`（工時、申請都是）。
- `attApproverOf_`：`hr_only` 一律回 false（表格上沒有人）。→ 只剩人資主管、admin（storeAttTargets_ 本來就放行）以及 att.extra 例外（同單位，總部同仁單位都是 dzy-hq）。
- 財務總監自己：職稱 hm 本來就不考勤，不受影響。
- 首頁提醒、營運系統名單：財務部同仁從財務總監的名單消失、人資主管照舊有 → 不會多出提醒。
- 考勤管理選單（Q4 選 B）：主要部門在清單內的總監（hm）**不再因職稱拿到** platform.att；其他來源照舊（人資主管、att.extra、att.view@<單位>、兼任店長）。其他選單不受影響。
- 不動：認領審核、人事異動、績效評核、請購簽核（都是別張表，stfReviewNeed_ 不改）。

## 2. 需求 2：兼任店長

### 2.1 設定方式
- 新個別例外功能碼 `store.sm@<單位代碼>`，顯示「兼任店長（<品牌 單位>）」，例 `store.sm@mzt-lzl`（台北六張犁）。
- 寫在既有「權限設定 → 個別例外」（perm_ex），沿用到期日、原因、撤銷、perm_audit 紀錄。
- **誰能設：admin 與人資主管**（人資主管不能設給自己，沿用 F7）。只能「多給」。
- 合法條件：單位存在、啟用、store 階梯；**不含央廚 ck**（央廚是廠長制，另案）。被設的人要在職。
- 不經 PERMS_ON：跟 att.view@ 一樣直接讀 perm_ex（`storeActingMap_()`：active、mode add、未過期、碼合法 → `{emp: [單位…]}`），掛進 storePeople_ 每人一欄 `acting_units`。
- 本人單位本來就是該店、或本人已是該店 sm → 無效果（不重複）。

### 2.2 效果（在職、單位在試點時）
把兼任者當作該單位的店長，**只在「核別人」時**：

| 地方 | 改法 |
|---|---|
| attApproverOf_ | need.kind 'unit'（計時／正職的工時與申請；店內其他打卡職稱的工時）且 need.unit ∈ approver.acting_units → 可核。**不能核自己**（一般店長可核自己工時的例外不適用）。head／brand_office 等上層照舊不給（跟一般店長一樣不能核店長／區經理本人申請） |
| 值班主管那條（F4） | **不改、照舊套用**：被核者是值班主管時，兼任者也是同店值班主管 → 不核，往上送。被核者不是值班主管（一般計時／正職）→ 這條根本不觸發，兼任者照核。跟「真店長也是值班主管」的行為一模一樣 |
| 支援到六張犁的別店同仁（storeSupportApprovers_ 第 1 層） | 兼任者算進第 1 層店長（§5 Q2） |
| 兼任者本人 | 完全照原身分：辦公室督導 → 同辦公室總監核（F5 已保證他的六張犁打卡帳號不算支援）；他的申請也照 req-upper 往上 |
| ident units_managed | 加入兼任單位（§5 Q1）→ 營運系統裡他在六張犁＝店長（整店功能、可排班） |
| platform.att／platform.sched／platform.storeops 閘門 | 有任一合法兼任單位（在試點）→ 開 |
| attUpperGaps（首頁「沒有上層」提醒） | 不改。兼任者不會變成任何值班主管的上層（他只補店長那層），所以不會讓提醒消失或多出來 |
| 收支作廢 void_units | 不給（店長本來也沒有，要另設 store.void） |

### 2.3 其他店長功能（Q3 選 B：一起給）

共同原則：**全部即時計算、不存副本**。兼任設定（perm_ex 一列）是唯一來源；撤銷、到期（到期日當天仍有效、隔天失效）、兼任者停用、該店停用 → 下一次動作就不再有。
已經做完的事（已核准的單、已簽的關、已送出的評分）不回頭改。管理系統畫面上的選單要重新整理才會消失，但後端每個動作都重算，選單還在也按不動。營運系統（門市營運、考勤、排班）最多 5 分鐘內重查身分。

| 功能 | 給了之後看得到什麼 | 能做什麼 | 實作點 |
|---|---|---|---|
| 同仁開通帳號審核（我的資料 → 待審核） | 六張犁送認領的人：姓名、填的單位職稱、**生日、手機、地址**（與店長相同） | 核准／退回六張犁的計時、正職認領（不能核店長本人的認領，同一般店長） | Staff.gs stfReviewScope_ 帶 `acting`，stfScopeMeets_ 加「兼任＝該店 rank 3 店長」比對 |
| 人事異動（離職／調職／調薪）第一關「直屬主管」，以及替同仁送人事單 | 六張犁計時、正職的人事單 | 簽第一關（調薪後面照舊人資、總經理）；也能替他們送離職／調職／調薪單（同一般店長，apvChainAbove_ 走直屬主管判斷；送出後照舊要人資、總經理簽） | 同上（apvDirectMembers_ 用 stfReviewScope_，自動跟著） |
| 請購、費用請款第一關（店長那一級，預設 0–5,000 元） | 六張犁同仁送的單 | 簽核 | ApprovalRoute.gs apvRoleMembers_ head：門市單位＝兼任單位也算；職級比照店長（不能簽店長本人送的單） |
| 績效評核打分 | 六張犁計時、正職的評核表 | 替他們打分（同店長範圍） | Eval.gs evScope_：有兼任就有「替所屬同仁打分」，範圍走同一套 stfReviewScope_ |
| 營運稽核、盤點抽查看店（同一個後端） | 六張犁的稽核紀錄、盤點紀錄 | 只看（店長本來也只看） | Perms.gs permSessionCompute_：稽核範圍加上六張犁；原本沒有任何稽核權限的人補「看自己店」 |

**刻意不給（不是店長功能、或店長本來就沒有）**：收支作廢（店長也要另設）、單位通訊錄（看的是主要身分的單位）、打卡端 manager.html 的主管鑰匙、總部「在主店建打卡帳號」。這幾項 Eason 若要，另案。

**風險（給 Eason 知道）**：兼任者是督導，本來就看得到同品牌（或負責區）的稽核與評核；新增的實質權力是「六張犁 5,000 元以下請購／請款簽核」與「六張犁新人的生日、地址」。建議兼任一律設到期日（例：一個月），到期前人資再延。
### 2.4 已知風險（未確認，現況就有、非本案造成）
若兼任者 A 也是負責六張犁的區督導（REGIONS_ON 已開），六張犁其他值班主管的申請：上層督導＝A 本人，但 A 也是六張犁值班主管被 F4 擋掉；該店「有督導」所以總監也不補 → 只剩人資主管。attUpperGaps 會列出這些人。上線後由人資看首頁提醒確認；要改要動 req-upper 的規則，另案。

## 6. 夜間審查後補的規則（2026-10-29，Codex 找到、已修）
- **有效兼任**只有一個判斷（Perms.gs permActingMap_）：兼任者在職、主要身分有效（單位職稱啟用且相符）、兼任店≠本人主要單位、兼任店在試點。所有功能只吃這份。
- 新增：本人主要單位就是那家店 → 擋（bad_target）；同人同店已有生效中的兼任 → 擋（dup）。
- 撤銷：同人同店所有生效中的兼任列一起撤（舊資料重複也收得乾淨）。
- 新增、撤銷都寫 perm_audit（added／removed＝store.sm@<單位>）。
- 請購請款改派（noRank）也不讓兼任者簽店長以上的單。
- ~~財務部同仁到門市打卡不算支援~~（2026-10-29 Eason 改）：總部同仁（含財務部）到門市打卡＝支援，工時由該店主管核（店長才知道上下班時間）；請假／加班／忘打卡等申請照原身分簽（部門總監；財務部＝人資主管），原單位主管工時只看。`StoreOps.gs storeIsHqTarget_`、`storeAttLists_` 的 reqByHome。品牌辦公室同仁照 F5 不算支援。
- 個人例外（2026-10-29 Eason）：`STORE_NOT_SUPPORT_EX = { DZY027: ['cf'] }`——財務部一位同仁固定在央廚上班，不算支援、薪水算總部 → 工時與申請都由人資主管核，央廚主管只看不核（`storeAttIsSupport_` 回 false，回到 #60 的財務部規則）。打卡端另在央廚設 `REQ_DEPT_EMPS`（申請）擋值班核定頁（mala-clock-in#15）。
- 兼任者本人（門市同仁）到兼任店支援打卡：先把他剔出候選再找層，店裡沒別的店長就往區經理／督導／總監（Fable 找到）。
- 財務部值班主管不進「找不到上層」提醒（表上本來就只有人資，Fable 找到）。
- 有效兼任也要求主要職稱符合單位限定（例：中央工廠沒有店長）。
- 已知不修：PERMS_ON 關時兼任者沒有「看兼任店稽核」與「績效評核打分」（正式環境 PERMS_ON 已開）；「我的權限」把兼任帶來的考勤／排班／門市營運選單標成「系統角色」（只是來源文字）；權限異動分頁的兼任碼只顯示門市代碼；待審核標題仍是主要單位名稱。
