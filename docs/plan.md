## 分階段的邏輯

每個 Phase 結束都要能**拿給人看、能被驗收**，不做「三個階段之後才第一次跑起來」的東西。
順序的理由：先把地基做完並驗證分層真的成立（Phase 1 的最後一項就是拿假模組去驗），
再搬體質好的稽核（Phase 2），最後搬要順手重整的宿舍（Phase 3）——把最不確定的留在地基已經穩固之後。

| Phase | 目標 | 里程碑（做到這裡就算這階段完成） | 估時 |
|---|---|---|---|
| 0 | 前置與保全 | 兩份正式試算表已備份存證；`~/dzy` 骨架與 git 就緒；平台試算表與 Apps Script 已建立並完成授權 | 半天 |
| 1 | 平台層地基 | **能登入、看到首頁卡片、能新增使用者**；拿一個假模組掛上去，平台層程式碼零改動就出現在首頁 | 3–4 天 |
| 2 | 稽核兩模組搬入 | **會計能在新系統從頭到尾完成一次稽核填報**（兩張表都可），既有八支 node 測試全過；店長帳號只看得到自己店 | 4–5 天 |
| 3 | 宿舍合約模組搬入 | **建單 → 簽約 → 點交全流程在新系統跑通**，資料寫入與舊系統完全一致 | 3–4 天 |
| 4 | 整合驗收與上線 | requirements.md §10 十一條驗收條件全數打勾；部署、發帳號、舊站確認仍可用 | 1–2 天 |

## Phase 0：前置與保全

先做保全再碰任何東西——這是 §0 鐵規的實作順序。

1. 兩份正式試算表各另存副本（檔名帶日期），截圖存證，路徑寫進 `docs/backup-log.md`
2. `~/dzy` 建 git repo（**先 private**，不設 Pages），目錄骨架依 spec §2
3. `.gitignore` 先寫好：`.clasp.json`、任何 `*secret*`、`*.local.*`
4. 建平台試算表「鼎兆元管理系統｜帳號權限」＋獨立 Apps Script 專案（clasp）
5. `Setup.gs` 建四個分頁與預設角色列，**通行碼與密碼一律手動填入試算表，不進 repo**
6. **Eason 手動在編輯器執行一次函式完成 OAuth 授權**（唯一需要他動手的事）

## Phase 1：平台層地基

由下往上做，每一層都有測試：

```
樣式 tokens ─→ fmt 工具 ─→ ui 元件
                   ↓
平台後端 Auth/Users ─→ auth.js（登入・session・can）
                              ↓
                          api.js（呼叫・轉接・店長裁切）
                              ↓
                          shell.js（路由・導覽・掛載）
                              ↓
                     registry.js ＋ 假模組驗證分層
```

**這個階段的驗收核心不是「畫面好看」，而是最後一項**：寫一個什麼都不做的假模組
`modules/demo/`，只加 `registry.js` 一行，它就要出現在首頁、能點進去、能顯示 badge——
平台層一行都不能改。這條過不了，代表分層沒做成，後面兩個 Phase 全部要重來，
所以它擺在 Phase 1 的最後，而不是專案最後。

## Phase 2：稽核兩模組搬入

搬遷策略是**逐檔搬、每搬一支就跑既有測試**，不做大爆炸重寫。

1. 先做 `modules/audit-shared/api.js`（共用快取），因為兩個模組都靠它
2. `audit-stock` 先搬（它的 `views/audit.js` 是全專案最大的一支，1157 行，要拆成三個任務）
3. `audit-ops` 後搬（結構較單純，且可以抄 `audit-stock` 已驗證的模式）
4. 兩模組各加一個「我的門市」分頁＝店長視角
5. 既有八支 node 測試接上新結構，**一支都不能少、不能改斷言**

搬遷時的規矩：既有 view 的 DOM 結構與 class 名盡量原樣保留，
這樣既有 e2e 測試的選擇器才不會全部失效——重整只做「拿掉重複、改成模組介面」，不順手改版面。

## Phase 3：宿舍合約模組搬入

這支要順手重整（現況三個 HTML 各自內嵌、`esc()` 三份、`API_URL` 三份）：

1. `modules/dorm/api.js`：`API_URL` 從此只有一處
2. 後台清單 → 建單 → 點交，三個 view 依序搬
3. `sign.html` 留在殼外，但改成 `import` 平台的 `fmt.js`／`ui.js`（簽名板從此只有一份）
4. **簽約流程本身一行邏輯都不改**，只換掉它用的工具函式來源

風險控制：每搬一個 view，就用測試 token 實跑一次對應動作，跑完清資料。
`sign.html` 改完必須用同一份測試 token 完整簽一次，確認與改之前的行為一致。

## Phase 4：整合驗收與上線

1. 六支 e2e 全跑（一次一支、間隔 20 秒，port TIME_WAIT 會衝突）
2. 逐項打勾 requirements.md §10，每一勾附實跑指令與輸出
3. 完工後比對兩份正式試算表列數與內容，與 Phase 0 的備份一致
4. 建 public repo ＋ Pages，發帳號給會計與五位店長
5. 確認舊網址 `/mala-audit`、`/mala-dorm` 仍正常
6. 收尾寫回：專案記憶一則、CLAUDE.md 路由表一列、dispatch-rules.md 第 2 節與第 5 節各一列

## 派工方式

`task.md` 的每個任務就是天然的派工單位（100–200 行、輸入輸出明確）。
搜尋盤點類派 haiku、實作與審查類派 sonnet，交辦 prompt 照 `~/.agents/institution/delegation-templates.md` 抄。
跨任務共用的格式定義一律以 spec.md §4 為準，任務內不得自訂。
每個 Phase 結束跑一次 fresh-context 對抗審查（範本 5），不給審查者工作過程、只給產出物與驗收條件。
