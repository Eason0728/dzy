版本：v3 / 2026-08-14（v3：取消宿舍長角色、美村南昌不發店長帳號、資料保全升為最高鐵規。已完成 Eason 確認）

## 0. 最高鐵規（違反此條，整個專案算失敗）

> **現有系統的資料都不能損壞、更改、遺失。**

這條的優先序高於本文件所有其他需求。任何一個功能如果做起來會碰到既有正式資料的風險，
寧可不做那個功能、寧可延後上線，也不許冒險。具體展開見 §8。

## 1. 一句話

把鼎兆元集團現有各自為政的內部系統，收進**一個網址、一次登入、一套權限**的管理系統殼；
第一批搬「稽核系統」與「宿舍合約系統」，架構要能讓之後每加一支系統只寫模組、不重做地基。

## 2. 要解決的問題

| # | 現況 | 痛在哪 |
|---|---|---|
| P1 | 每支系統一個網址（`/mala-audit`、`/mala-dorm`…），靠手機書籤與 LINE 舊訊息找入口 | 使用者記不住、找不到；新同仁要人一個一個發連結 |
| P2 | 每支系統一組通行碼，稽核一組、宿舍後台另一組 | 一天打兩次碼；碼外流時要一支一支換；沒人知道誰有哪支的碼 |
| P3 | 權限散在各系統內（稽核有會計／主管兩角色，宿舍後台只有一組碼不分人） | 沒辦法回答「這個人能看到什麼」；離職要一支一支關 |
| P4 | 每加一支新系統，登入頁、導覽、樣式、API 封裝都重寫一次 | 十支系統十套地基；宿舍合約更是 `esc()` 複製三份、`API_URL` 寫三份 |
| P5 | 看起來不像一家公司的系統 | 對內沒有「集團在數位化」的整體感，對店長的推動力弱 |

## 3. 使用者與角色

不登入也能用的例外先講：**員工的宿舍簽約連結（token 連結）維持免登入**，那是發給不會有帳號的人的一次性連結，留在殼外。

| 角色 | 是誰 | 進來要做什麼 | 稽核 | 宿舍合約 |
|---|---|---|---|---|
| 系統管理者 | Eason | 管帳號、管角色、全系統巡查 | 全部 | 全部 |
| 部門主管 | 品牌主管／督導／人資主管 | 看稽核結果；辦宿舍合約全流程 | 全節點唯讀 | 建單、發連結、點交、終止 |
| 會計 | 總部會計 | 到五個節點做月初盤點抽查、金庫抽查、營運稽核 | 填單＋報表（全節點） | 無 |
| 店長 | 稽核五節點的現場負責人 | 看自己店被稽核出什麼問題、還有哪幾項沒改 | **只看自己節點**、唯讀 | 無 |
| 員工 | 要簽宿舍合約的同仁 | 開連結、簽名、送出 | 無帳號 | 走 token 連結 |

**店長帳號只發給稽核涵蓋的五個節點**：小辛辣光復、中央廚房、墨竹亭光復、墨竹亭金山、墨竹亭六張犁。
小辛辣美村、南昌不在稽核範圍內，**不發帳號**（Eason 2026-08-14 指示）。

**兩個由此而來的架構要求：**
- 帳號除了「角色」還要帶**所屬節點**（店長王小明＝小辛辣光復）；權限判斷是「角色決定看得到哪些模組」＋「所屬節點決定看得到哪些資料」兩層。
- 角色與模組的對照表要做成**可設定**，不是寫死在程式裡——之後加調撥系統時只加一列，不改程式。

## 4. 範圍

**這次要做（Phase 1–3）**
1. 平台殼：登入、角色權限、導覽、首頁、共用樣式與共用工具
2. 稽核模組搬入（現有功能一項不減：兩張表、五節點、抽樣、報表、追蹤清單）＋新增店長唯讀視角
3. 宿舍合約模組搬入（後台＋點交搬進殼；簽約頁留在殼外，只做去重）

**這次不做、但架構要預留**
- 調撥系統（`~/mala-transfer`）＝下一支要進來的，殼的模組介面必須先能接住它
- 人資類（打卡／排班／評鑑）、營運類（庫存／耗損／損益）＝更之後，本次只確保「多加一個模組不用改地基」

**明確不做（YAGNI）**
- 不動兩支後端 Apps Script 的商業邏輯（見 §5 D3）
- 不做單一登入 SSO／Google 帳號登入（第一版帳密即可）
- 不做行動 App、不做離線模式
- **不做完整的跨模組儀表板**——改成首頁卡片帶一個待辦數字（D9），等三四支模組都進來、資料夠厚再升級

## 5. 已定案的決策

| # | 決策 | 為什麼 |
|---|---|---|
| D1 | **真整合**：兩套前端進同一個 repo，共用登入／導覽／樣式，單一網址 | Eason 2026-08-14 選定。只有這種做法之後加系統才會便宜 |
| D2 | **一套集團帳號＋角色**：一人一組帳密，角色決定看得到哪些模組 | Eason 2026-08-14 選定。解 P2、P3 |
| D3 | **兩支後端 Apps Script 不動**（不合併、不改商業邏輯） | §0 鐵規。宿舍合約是法律文件、稽核有正式歷史資料；殼只做前端整合＋新增一支「帳號權限」後端 |
| D4 | **新網址 `eason0728.github.io/dzy`，舊網址保留可用** | 會計手機有書籤、簽約連結已發在 LINE，不能斷 |
| D5 | 技術棧沿用原生 HTML/CSS/JS＋GitHub Pages＋Apps Script，零建置零相依 | 與現有九支系統一致，Eason 一個人維護得動；無 build step 代表半年後還能改 |
| D6 | 手機優先（mobile-first），桌機是加分 | 稽核是會計現場手機填單，這是主戰場 |
| D7 | 主色沿用鼎兆元紅 `#c8402c`，設計走乾淨有質感、不灑裝飾 | 品牌識別正本；宿舍合約現用色即此 |
| D8 | **分層建構**（Eason 指定）：平台層／模組層／資料層三層，層與層之間只透過明訂介面往來 | 見 §6 |
| D9 | 首頁＝**模組卡片＋待辦數字**（例「稽核系統 · 3 項未完成」），不做完整儀表板 | Eason 2026-08-14 選定。數字由**模組自己吐出來**，平台層只負責顯示，才不會破壞 D8 |
| D10 | 店長**只看得到自己節點**的稽核結果，唯讀 | Eason 2026-08-14 選定。稽核抓到的問題店長自己看得到，不用等人轉達——直接打在「店長執行力」這個卡點上 |
| D11 | **不設「宿舍長」角色**，宿舍合約後台歸部門主管 | Eason 2026-08-14 指示取消 |

## 6. 分層要求（本案的核心約束）

| 層 | 負責 | 規矩 |
|---|---|---|
| **平台層**（殼） | 登入、身分與角色、所屬節點、導覽、路由、共用樣式、共用工具（提示訊息、載入中、對話框、日期格式、HTML 轉義、簽名板） | 不得認識任何一個模組的業務邏輯；只認識「模組清單」這份設定 |
| **模組層** | 稽核、宿舍合約（未來：調撥…） | 每個模組是一個資料夾，自帶 `manifest`（代號、名稱、圖示、需要的權限、進入點、待辦數字怎麼算）；只能透過平台層給的介面取得身分、呼叫後端、畫 UI |
| **資料層** | 各模組自己的 Apps Script 後端＋Google 試算表，另加一支新的「帳號權限」後端 | 模組不得直接摸別的模組的試算表 |

驗證這個分層有沒有做成功的標準只有一條：**新增第三個模組（調撥）時，平台層的程式碼一行都不用改**，只需新增一個模組資料夾＋在模組清單加一列。

## 7. 核心功能

### 平台層
- F1 登入頁：帳號＋密碼，後端驗，錯誤次數限制
- F2 登入後首頁：只顯示「這個角色有權限的模組」卡片，每張卡片一句話說明＋一個待辦數字
- F3 導覽：手機用底部／漢堡選單，桌機用側邊；隨時可切模組、可登出
- F4 人員管理（僅系統管理者）：新增／停用帳號、指派角色與所屬節點、重設密碼
- F5 共用工具：提示訊息、載入中、確認對話框、日期格式、HTML 轉義、簽名板——各一份，禁止複製第二份

### 稽核模組（功能與現況等價，唯一新增是店長視角）
- F6 兩張表：①營運稽核表 19 項（消防安全／營運／環境清潔／食安）②月初盤點抽查 20 項＋金庫抽查
- F7 五節點：小辛辣光復、中央廚房、墨竹亭光復、墨竹亭金山、墨竹亭六張犁
- F8 抽樣、只填異常項模式、草稿、報表、合格率、未完成追蹤清單
- F9 原本的「會計／主管」通行碼角色，改由平台層角色決定
- F10 **新增**：店長視角＝自己節點的合格率、被抓到的問題、未完成追蹤清單，唯讀

### 宿舍合約模組
- F11 後台：建合約單、產簽約連結、合約清單與狀態、終止合約
- F12 點交：開退宿點交單、設備檢查、賠償計算、簽名
- F13 簽約頁（殼外）：員工開 token 連結、身分驗證、設備點收、手簽、送出
- F14 現有的每日 03:00 到期檢查與 PDF 產製維持不變

## 8. 資料保全（§0 鐵規的具體展開）

搬遷前後，這些必須一模一樣：

- R1 稽核系統寫進「2026年月初盤點及金庫抽查明細表」的欄位、格式、分頁完全不變
- R2 宿舍合約寫進 `contracts`／`handovers`／`settings`／`audit_log` 的欄位完全不變
- R3 已發出去的簽約 token 連結仍然可以開、可以簽
- R4 舊網址 `/mala-audit`、`/mala-dorm` 仍可正常使用（過渡期雙軌）
- R5 兩支 Apps Script 的部署 ID 與網址不變（絕不 `create-deployment`）
- R6 **正式資料零刪改零遺失**：不執行任何刪除列、清空分頁、覆寫欄位的動作
- R7 **開發期間一律打測試資料**，不碰正式列；測試資料事後清乾淨（沿用既有 `cleanupTestContracts`／`cleanupE2E`）
- R8 **動工前先把兩份試算表各備份一份**（另存副本，存證日期），出事有得還原
- R9 既有的每日 03:00 到期檢查、既有排程與觸發器不得被停用或改時間
